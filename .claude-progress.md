### Security detour (2026-08-19) — relevant context for anyone touching this hosting account

Before any of the above, discovered the `skoder` cPanel account (which hosts ~35 unrelated sites, not just this project) had been compromised since **2026-06-10** via a Laravel Ignition RCE (CVE-2021-3129 class — `APP_DEBUG=true` + `ignition` package exposed in production on multiple independent Laravel deployments on the account). Confirmed via access logs (real `200` responses to `POST /_ignition/execute-solution`, not just blocked probes). Because every site on the account shares one Linux user, that one breach gave account-wide filesystem access, leading to four separate mass-webshell-drop waves (Jul 17, Aug 8, Aug 16, Aug 17) — and the account owner had already found and cleaned this twice before (Aug 8–9, Aug 12) without closing the actual hole, so it kept coming back.

Remediated as part of this session:
- Flipped `APP_DEBUG` false on the 8 sites still exposed.
- Removed 747 individual webshell files + 657 entire malicious directory trees (~1,400 objects total) across the account, using content-signature + creation-timestamp verification per file (not blind pattern deletion — two files that looked suspicious by heuristic turned out to be genuine Laravel front controllers and were left alone).
- Evidence archived to `~/incident_evidence/malware_removed_20260819_044322.tar.gz` before deletion.
- **Not done, and outside this project's scope**: full credential rotation account-wide, patching/redeploying the other ~30 unrelated sites, confirming with whoever else has access to this account. Flagged to the user directly — this is bigger than Blood Connect JU and belongs to the account owner's broader incident response, not something to silently fold into this repo's history.

## Phase 2 — Donor profiles ✅ (2026-08-19)

`donor_profiles` table already existed (created in Phase 1 for onboarding), so this phase is the eligibility accessor, a real profile page, and — new beyond the original brief — letting users *edit* their donor info after onboarding, not just set it once.

- `DonorProfile::is_eligible` accessor: null `last_donation_date` or more than 120 days ago. Hit a real Carbon 3 bug while writing the boundary test: `diffInDays()` returns a **signed float**, not an absolute integer, and the `date` cast normalizes to midnight while `now()` carries the current time — comparing them directly made the eligibility boundary drift by up to ~24h depending on what time of day the check ran, and an early version of the fix had the diff direction backwards (comparing `-121 > 120`, always false). Fixed by normalizing both sides to `startOfDay()` before diffing, in the direction that yields a positive value. Caught by a deliberately picked boundary test (119/120/121 days), not general coverage — the lesson: floating-point day diffs need explicit day-granularity normalization, don't assume integer truncation.
- `nextEligibleDate` accessor for the "eligible again in N days" UI hint.
- `UpdateDonorProfileRequest` extracted as a shared form request — the onboarding wizard and the profile page now validate identically (real hall/department list, hall required only for students) instead of maintaining two copies of the same rules.
- `User::updateDonorProfile()` — same reasoning, one place that writes both the `users` columns and the `donor_profiles` row, called from both `OnboardingController` and the new `ProfileController::updateDonorProfile`.
- Fixed a real bug inherited from Phase 1's onboarding form along the way: unchecked HTML checkboxes don't submit at all, so "turn off availability" was silently ignored (`is_available` request key just wouldn't be present, and the fallback defaulted true). Fixed with the standard hidden-input-plus-checkbox pairing, in both the onboarding wizard and the new profile form, with a regression test.
- Profile page (`profile/edit.blade.php`) restyled to the brand shell and reorganized: new donor-profile section first (blood group, hall/department, phone, availability, live eligibility badge, trust score), then account info, password, delete account — all as `surface-panel` cards using the established component set.

## Phase 4 — Matching & response ✅ (2026-08-20)

- `request_responses` table (unique on `[request_id, donor_id]` — a donor can respond to a given request exactly once, enforced at the DB level, not just the policy) and the `RequestResponse` model.
- Real ABO/Rh compatibility matrix (`BloodRequest::DONOR_COMPATIBILITY`), not just exact-blood-group matching — O- is the universal donor, AB+ the universal recipient, etc. Hardcoded as a const array rather than computed, because the mapping is small, fixed by medical fact (won't change), and a lookup table is far easier to verify by inspection (and to unit-test exhaustively) than blood-type arithmetic.
- `DonorProfile::scopeMatchingRequest()`: eligible + compatible donors for a request, ranked exact-blood-group-first, then same-hall-or-department-first, then available-first. Excludes the requester themselves even if they happen to be a compatible donor.
- Two `database`-channel notifications: `RequestResponded` (to the requester, sent synchronously on response — it's a single targeted notification, no reason to queue it) and `NewMatchingRequest` (to every eligible compatible *available* donor when a request is created — this one fans out to potentially dozens of donors, so it's dispatched via a queued job instead, `NotifyMatchingDonors`, fired from a `BloodRequestObserver::created` hook rather than inline in the controller).
- Brought the `notifications` table forward from its nominal Phase 7 slot, same reasoning as Phase 1 pulling `donor_profiles` forward — the feature needs it now, no reason to fake it and redo the migration later.
- Queueing decision: `QUEUE_CONNECTION=database`, but the `skoder` shared-hosting account has no supervisor/persistent-process access, so there's no long-running `queue:work` daemon. Instead `queue:work --stop-when-empty --max-time=50` is added to `routes/console.php`'s scheduler, running `everyMinute()` alongside `requests:expire`, riding the same cron that already drives `schedule:run`. Not as low-latency as a real worker, but correct and free on this hosting tier — flagged here in case this ever moves to infrastructure where a real daemon is possible.
- `RequestResponseController`: `store` (donor responds — policy-gated: not the requester, request still open/donor_found, donor eligible and compatible, hasn't already responded) and `confirm` (requester picks a specific responder — policy-gated: only the requester, only while the response is still `responded` not already `confirmed`).
- `DonorSearchController` (`/donors`) — browsable, filterable (blood group, hall) donor directory, eligible donors only. Had to be written directly rather than via `make:controller --invokable`, because `artisan` couldn't boot to run the generator once `routes/web.php` already referenced the not-yet-existing class — a one-off tooling quirk, not a design decision.
- Request detail page: "I can donate" button (donor-eligible-only, via `@can`), responder list with per-response "Confirm" action visible only to the requester, confirmed responders shown with a badge to everyone else.
- Tests: 84 passing (21 new) — compatibility matrix (universal donor/recipient, partial compatibility), ranking (exact-group-first, same-hall-first, excludes ineligible, excludes the requester), the full respond/confirm authorization matrix (compatible, incompatible, ineligible, already-responded, non-requester-confirm), both notification paths (`Notification::fake()` — sent on response, sent to matching available donors, not sent to unavailable/incompatible donors), donor search listing + both filters.
- While writing these tests, found and fixed a self-inflicted bug: the `requester()` test helper originally didn't complete onboarding (no `DonorProfile`), which broke the *confirm* test once that action was correctly placed behind the same `onboarded` middleware as everything else — fixed the helper to create a profile by default, then fixed the two tests that had been manually creating a second profile for the same user (which now violated the new unique constraint on `donor_profiles.user_id` once the helper did it automatically).

## Phase 5 — Trust & safety ✅ (2026-08-20)

- **Verifier queue**: `VerificationQueueController` (mixing an invokable `__invoke` for the GET with regular `approve`/`reject` methods on the same class — an unusual shape, but it's what the brief's own route table (Section 6) specifies literally, so kept it rather than splitting into three controllers for no functional gain). Gated by `role:verifier,admin`, deliberately **not** `onboarded` — verifiers are assigned their role by an admin (Phase 1 note), not self-selected, and shouldn't need a donor profile just to review requests. New `BloodRequest::scopeAwaitingVerification()` (unverified, not rejected, still `open`/`donor_found`) keeps the queue from filling up with already-expired or already-fulfilled noise.
- **Reject needed a real state**, not just a UI label: the `blood_requests.status` enum has no `rejected` value (and it's already live in production, not something to redefine mid-project), so rejecting sets `status = expired` — same effect on the public feed as a natural timeout — plus new `rejected_at`/`rejected_by` columns so a verifier's rejection stays distinguishable from an ordinary 72h expiry in the data, even though both currently render the same "Expired" pill.
- **Report**: went with the brief's "lightweight `reports` table" option over a bare boolean — a `reason` (fixed set: spam/fraudulent/duplicate/inappropriate/other) plus optional free-text `details`, unique on `[request_id, reporter_id]` so the same person can't spam-report one request. The actual moderation review UI is explicitly Phase 8 territory ("moderation queue for flagged requests" is listed under 5.6 Admin Dashboard in the brief) — this phase only builds the reporting side and the data it needs to be reviewable later, not the reviewing.
- **Mutual fulfillment confirmation** was the trickiest design call this phase. The brief says: "After a request is marked Fulfilled, both requester and donor get a mutual confirmation prompt; confirming both sides writes a donation_history row and bumps trust_score." Phase 4 already has a `confirm` action where the requester picks which responder helped — but that's donor *selection*, not an attestation that the donation physically happened, and it can occur before fulfillment. So this phase adds a second, independent pair of signals: `requester_confirmed_at`/`donor_confirmed_at` timestamps on `request_responses`, settable only once each, only by the matching side, and only once the parent request is `fulfilled`. `RequestResponseObserver::updated()` watches for the update that leaves *both* timestamps set — necessarily exactly one such update, since each side can only transition null → timestamp once — and on that transition writes a `donation_history` row and increments the donor's `trust_score`, so the side-effect lives in the observer rather than being duplicated across two controller branches.
- `donation_history` brought forward from its nominal Phase 6 slot, same reasoning as `donor_profiles` (Phase 1) and `notifications` (Phase 4) before it — the feature needs it now.
- Request detail page updates: a collapsible "Report this request" form (Alpine-toggled, reused the app's existing radio-pill pattern from the request-creation form rather than introducing a bare `<select>`), and per-responder mutual-confirmation UI once a request is fulfilled — shows "waiting on the donor/requester" to whichever side has already confirmed, a "Confirm donation" button to whichever side hasn't, and a shared "confirmed by both sides" badge once complete. Handles the case (units_needed > 1) where a request can have *multiple* confirmed responders, each with independent confirmation state, not just one.
- Added `x-cloak` (`[x-cloak] { display: none !important; }`) to `app.css` — the first Alpine-toggled block that starts closed (the report form); without it, Alpine's own hide-on-init would otherwise flash the form open for a beat before Alpine attaches.
- Tests: 99 passing (15 new) — verifier queue reachability without onboarding, non-verifier forbidden, queue scoping, approve/reject state changes, can't re-verify an already-verified request; reporting (create, duplicate-report rejected, invalid-reason rejected); mutual confirmation (not logged until both sides confirm, logged + trust_score bumped once both do, order-independence, bystanders forbidden, can't confirm pre-fulfillment, can't confirm the same side twice).
- Manually walked the entire phase against a live dev server: seeded a requester/donor/verifier via `tinker`, approved a request through the real verifier queue UI, reported it as the donor and confirmed the row landed with the right reporter/reason, ran the full respond → confirm-donor → fulfill (both steps) → mutual-confirm sequence over real HTTP requests in both directions and watched `donation_history` populate and `trust_score` increment only after the second confirmation, then separately exercised the reject path on a second seeded request and confirmed `status`/`rejected_at`/`rejected_by` all landed correctly. Cleaned up the smoke-test data afterward.

## Phase 6 — Engagement ✅ (2026-08-20)

- `donation_history` already existed (brought forward in Phase 5, since mutual confirmation needed somewhere to write). This phase adds `badges` and `donor_badges` on top of it.
- **Badge catalog is seeded inside the `create_badges_table` migration itself**, not a `DatabaseSeeder` (that's explicitly Phase 9 territory in the brief, and reserved for environment-specific sample data — users, sample requests). The three badges (First Donation, 5-Time Donor, Rare Donor) are reference/catalog data, not environment-specific, so seeding them as part of the migration guarantees they exist in every environment that runs `migrate` — local, CI's sqlite, and production — with no separate step anyone could forget.
- **`DonationHistoryObserver::created()`** is the award engine, matching the brief's instruction literally ("award badges via model events/observers when donation-history milestones are hit"). It's a separate observer from Phase 5's `RequestResponseObserver` (which writes the `donation_history` row and bumps `trust_score`) — reacting to the row's *creation* rather than folding badge logic into the mutual-confirmation controller keeps those two concerns apart, and it means badges get awarded correctly regardless of how a `donation_history` row comes to exist (mutual confirmation today, a manually-logged off-platform donation later). Each award is guarded by an existence check before `attach()`, so re-processing the same donor never double-awards.
- **"Rare blood type" defined as Rh-negative** (`A-`, `B-`, `AB-`, `O-`) — genuinely rare in the Bangladeshi population (~3-5%), not just the textbook-universal `O-`/`AB+` — checked on every donation rather than gated to the first, since it's about donor identity rather than a countable milestone (idempotent `attach()` guard makes this safe either way).
- **Leaderboard** groups by `COALESCE(users.hall, users.department)` rather than the brief's original single `hall_or_department` field, consistent with Phase 1's split into two real columns. Cached 5 minutes (`Cache::remember`) per the brief's "cached briefly" — the array-driver-per-test-process behavior means this doesn't leak stale state across tests, so no extra cache-clearing scaffolding was needed for the test suite.
- Profile page gets a new "Donation history & badges" panel: earned badges as a row of pills (title-attribute tooltip carries the description), donations as a simple timeline (hospital name + date, falling back to "Off-platform donation" for the nullable `request_id` case the brief's schema allows for but this app doesn't currently produce).
- Tests: 109 passing (10 new) — badge thresholds (1st donation, not-yet-5th, 5th, rare type awarded/not-awarded by group, never double-awarded), profile page shows donation history and badges, leaderboard ranks by donation count and handles the empty case.
- Manually verified against a live dev server: seeded a donor with an Rh-negative blood group and a directly-created `donation_history` row (bypassing the HTTP mutual-confirm flow on purpose, to prove the observer reacts to the row itself, not the controller action that usually creates it) and confirmed both `first-donation` and `rare-blood-type` badges landed; loaded `/profile` and saw both badges and the donation-history entry render; loaded `/leaderboard` and saw the donor's hall ranked; added four more donations via `tinker` and confirmed `five-time-donor` awarded exactly at the fifth. Cleaned up the smoke-test data afterward.

## Phase 7 — Notifications ✅ (2026-08-20)

**Scope changed from the original plan, by explicit user direction:** the brief's SMS channel stub is skipped entirely — no `SmsChannel`, no provider decision to defer. ## Phase 8 — Admin dashboard ✅ (2026-08-20)

- Stat cards (`AdminDashboardController`): donors grouped by blood group, fulfilled vs. expired request totals, total/active user counts, pending-report count, and average first-response time. That last one is computed in PHP over a new `BloodRequest::firstResponse()` relation (`hasOne(...)->oldestOfMany()`) rather than a raw `TIMESTAMPDIFF` query — the latter is MySQL-only and would silently break the test suite, which runs on sqlite.
- **"Deactivate" means deactivate, not delete** — the brief's user-management spec says "deactivate," and this app's FKs cascade-delete a user's donor profile, donation history, and requests, so an actual `DELETE` would destroy real records an admin investigating a problem account almost certainly wants to keep. New `is_active` boolean on `users` (default `true`); `AdminUserController@destroy` (the resource's `DELETE` verb) and `@update` both just flip it off — no row is ever removed.
- **Self-lockout guards, in two different layers for two different actions**: `UpdateUserRequest` blocks an admin from deactivating their own account or changing their own role away from admin (a validation-level check, since it's about *which values* are being submitted); `AdminUserController@destroy` separately blocks self-deactivation via that route too (`abort_if`), since destroy doesn't go through the same form request. Both are covered by tests — without them, an admin editing their own row for an unrelated reason could accidentally lock every admin out of the account with no way back in short of direct database access.
- **Deactivation had to be enforced in three places, and two of them were real bugs I found while wiring the third**: (1) `LoginRequest::authenticate()` — rejects a login attempt outright. (2) `GoogleAuthController::callback()` — same check before `Auth::login()`. (3) new global `EnsureAccountIsActive` middleware, appended to the whole `web` group (not just gated route groups) — catches a session that was already active *before* an admin deactivated it, logging it out and invalidating it on its very next request, rather than leaving it valid until it naturally expires. ## Real-time updates via Laravel Reverb (web) ✅ (2026-08-31)

User asked whether real-time page updates were possible on both web and Android; after being shown a lighter push-triggered-refresh alternative, explicitly chose full WebSockets via Laravel Reverb, and explicitly asked for the notification bell to be included, not deferred — see the plan at the time (`.claude/plans` — the "Real-time updates via Laravel Reverb" plan) for the full design writeup. This entry covers the backend + web half; Android's half is tracked in its own repo's progress log.

- **Key finding that reshaped the plan**: a real-time notification bell needed more than a broadcast channel — every notification class involved (`NewMatchingRequest`, `RequestResponded`, `DonorSelected`, `RequestVerified`, `RequestRejected`, `DonationConfirmed`, `DonationConfirmationPending`) was `ShouldQueue`, and the only queue drain was a once-a-minute cron (`queue:work --stop-when-empty`, `routes/console.php`) — up to 60s of latency that would have made the new broadcast channel pointless for anything still riding the queue. Fixed by adding a **real persistent `queue:work` process** (supervisord-managed, `--tries=3`, `autorestart=true`) alongside Apache and Reverb in the same container — the old cron entry is retired (comment left in `routes/console.php` explaining why, not silently removed).
- **Three broadcast channels**, all covered by exactly two new events (`App\Events\RequestFeedUpdated` on public channel `requests`, `App\Events\RequestActivityUpdated` on public channel `request.{id}`), both `ShouldBroadcastNow` (bypasses the queue entirely — cheap enough not to need it, and this is what actually makes the feed/detail page instant) — fired from `BloodRequestObserver`'s `created()`/new `updated()` and `RequestResponseObserver`'s new `created()`/existing `updated()` (broadened to also cover the `status` change a donor-selection produces, which the existing confirmation-timestamp-only guard didn't catch). No controller changes needed — every hook point is already Eloquent-event-driven. The third channel, `private-App.Models.User.{id}`, is Laravel's built-in per-notification broadcasting — each notification class above gained `'broadcast'` in `via()` and a `toBroadcast()` (wraps the existing `toArray()`, no new payload shape).
