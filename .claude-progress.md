## Infrastructure — production hosting + CI/CD ✅ (2026-08-19)

- **Live at https://blood.deshlet.com** — cPanel subdomain on the `skoder` shared hosting account, docroot `public/`, PHP 8.2 (`ea-php82`), Node 22 (via nvm, installed alongside the account's existing Node 18 default — not changed globally).

- Deploy key (`ed25519`, no passphrase) authorized in cPanel's SSH access; stored as an encrypted secret (`SSH_PRIVATE_KEY`) on the GitHub repo alongside `SSH_HOST`/`SSH_PORT`/`SSH_USER`/`DEPLOY_PATH`.
- `.github/workflows/deploy.yml`: on push to `main`, waits for the `tests` workflow to pass first (`lewagon/wait-on-check-action`), then SSHes in (`appleboy/ssh-action`) and runs `git reset --hard origin/main` → `composer install --no-dev` → `npm ci && npm run build` → `migrate --force` → cache rebuild. Deploys never happen on a red build.

### Security detour (2026-08-19) — relevant context for anyone touching this hosting account

Before any of the above, discovered the `skoder` cPanel account (which hosts ~35 unrelated sites, not just this project) had been compromised since **2026-06-10** via a Laravel Ignition RCE (CVE-2021-3129 class — `APP_DEBUG=true` + `ignition` package exposed in production on multiple independent Laravel deployments on the account). Confirmed via access logs (real `200` responses to `POST /_ignition/execute-solution`, not just blocked probes). Because every site on the account shares one Linux user, that one breach gave account-wide filesystem access, leading to four separate mass-webshell-drop waves (Jul 17, Aug 8, Aug 16, Aug 17) — and the account owner had already found and cleaned this twice before (Aug 8–9, Aug 12) without closing the actual hole, so it kept coming back.

Remediated as part of this session:
- Flipped `APP_DEBUG` false on the 8 sites still exposed.
- Removed 747 individual webshell files + 657 entire malicious directory trees (~1,400 objects total) across the account, using content-signature + creation-timestamp verification per file (not blind pattern deletion — two files that looked suspicious by heuristic turned out to be genuine Laravel front controllers and were left alone).
- Evidence archived to `~/incident_evidence/malware_removed_20260819_044322.tar.gz` before deletion.
- **Not done, and outside this project's scope**: full credential rotation account-wide, patching/redeploying the other ~30 unrelated sites, confirming with whoever else has access to this account. Flagged to the user directly — this is bigger than Blood Connect JU and belongs to the account owner's broader incident response, not something to silently fold into this repo's history.

## Phase 1 — Auth & roles ✅ (2026-08-19)

Two deliberate deviations from the original brief, both by explicit user direction:

- **No university-email restriction.** The brief's `ALLOWED_EMAIL_DOMAIN` gate was dropped entirely (env var removed) — alumni and others without a `juniv.edu` address need to be able to register. Any valid, unique email is accepted.
- **`hall_or_department` split into two real columns**, `hall` and `department`, instead of the brief's single combined field. The reference UI (`onboarding.tsx`) already treats them as distinct concepts, and real JU data confirms they should be: 21 halls (residential, students only) vs. 34 departments across 6 faculties (everyone). Pulled live from https://juniv.edu and hardcoded into `config/juniv.php` — used for both the onboarding selects and server-side validation (`Rule::in(...)`), so a submitted hall/department has to be a real one.

Built:
- Migrations (new files, not edits — production already ran the base `users` migration): `role` enum, `hall`, `department`, `phone`, `google_id` (nullable unique) on `users`; `password` made nullable (Google-only accounts have none); new `donor_profiles` table (brought forward from the nominal Phase 2 slot because the onboarding flow needs somewhere to write blood group / availability — Phase 2 now just adds the eligibility accessor + profile page on top of a table that already exists).
- `role` middleware (`role:admin`, `role:verifier,admin`) and `onboarded` middleware registered as aliases in `bootstrap/app.php` — `onboarded` gates `/dashboard` (and will gate future donor-facing routes) but deliberately **not** `/profile`, so account settings stay reachable even with an incomplete profile.
- **Google OAuth** via Laravel Socialite: `GoogleAuthController@redirect/callback`. First-time Google sign-in creates the user with `email_verified_at` set immediately (via `forceCreate`, since that column is intentionally excluded from `$fillable` everywhere else) — no OTP/email-verification step, matching the brief that Google already vouches for the address. If the Google email matches an existing password-based account, it's linked (`google_id` backfilled) rather than duplicated. Either path lands on `/dashboard`, which the `onboarded` middleware bounces to `/onboarding` until blood group/department/(hall) are filled in.
- Registration form now also collects `role` (student/staff/faculty — verifier/admin are assigned by an admin, not self-selected).
- Onboarding wizard (`onboarding.blade.php`): 3-step Alpine UI, single POST on submit. Hall is required only for students (staff/faculty only need a department). Re-opens on the correct step if server validation fails, instead of always resetting to step 1.
- Restyled to the brand shell: new `x-auth-card` component (mirrors the reference's `AuthShell`), `x-google-button`, and rebuilt `login`, `register`, `forgot-password`, `reset-password`, `verify-email` views. Shared field components (`x-text-input`, `x-input-label`, `x-input-error`, `x-auth-session-status`) restyled to the design tokens; `confirm-password` and the profile partials were left on Breeze's old styling since they're explicitly Phase 2 territory.
- `MustVerifyEmail` activated on the `User` model (was present but commented out by Breeze's scaffold) — regular signups now actually go through the verify-email gate; Google signups skip it as above.
- Tests: 39 passing (14 new) — any-domain registration, role validation/persistence, full Google OAuth flow (new user, existing-google-id login, email-linking, skip-verification, onboarding redirect — Socialite mocked via `Mockery`), onboarding middleware gating, hall-required-for-students-only, real hall/department validation.
- Manually walked the real HTTP flow end-to-end (not just feature tests) against the dev server: register → verify-email gate → (mark verified) → onboarding redirect with live juniv.edu data rendered → dashboard.

**Still on Breeze's old styling, deferred to Phase 2 as planned:** `confirm-password.blade.php`, `dashboard.blade.php`'s actual content.

**Update:** Google Cloud Console credentials received and configured (local `.env` + production, config cache refreshed) — confirmed live: `/auth/google/redirect` on production resolves to a correct Google OAuth URL with the right `redirect_uri` and scopes.

## Phase 2 — Donor profiles ✅ (2026-08-19)

`donor_profiles` table already existed (created in Phase 1 for onboarding), so this phase is the eligibility accessor, a real profile page, and — new beyond the original brief — letting users *edit* their donor info after onboarding, not just set it once.

- `DonorProfile::is_eligible` accessor: null `last_donation_date` or more than 120 days ago. Hit a real Carbon 3 bug while writing the boundary test: `diffInDays()` returns a **signed float**, not an absolute integer, and the `date` cast normalizes to midnight while `now()` carries the current time — comparing them directly made the eligibility boundary drift by up to ~24h depending on what time of day the check ran, and an early version of the fix had the diff direction backwards (comparing `-121 > 120`, always false). Fixed by normalizing both sides to `startOfDay()` before diffing, in the direction that yields a positive value. Caught by a deliberately picked boundary test (119/120/121 days), not general coverage — the lesson: floating-point day diffs need explicit day-granularity normalization, don't assume integer truncation.
- `nextEligibleDate` accessor for the "eligible again in N days" UI hint.
- `UpdateDonorProfileRequest` extracted as a shared form request — the onboarding wizard and the profile page now validate identically (real hall/department list, hall required only for students) instead of maintaining two copies of the same rules.
- `User::updateDonorProfile()` — same reasoning, one place that writes both the `users` columns and the `donor_profiles` row, called from both `OnboardingController` and the new `ProfileController::updateDonorProfile`.
- Fixed a real bug inherited from Phase 1's onboarding form along the way: unchecked HTML checkboxes don't submit at all, so "turn off availability" was silently ignored (`is_available` request key just wouldn't be present, and the fallback defaulted true). Fixed with the standard hidden-input-plus-checkbox pairing, in both the onboarding wizard and the new profile form, with a regression test.
- Profile page (`profile/edit.blade.php`) restyled to the brand shell and reorganized: new donor-profile section first (blood group, hall/department, phone, availability, live eligibility badge, trust score), then account info, password, delete account — all as `surface-panel` cards using the established component set.
- Handled a gap Phase 1's Google OAuth work opened: accounts created via Google have no password (`password` nullable), so the stock Breeze password-change form would be permanently broken for them (`current_password` can never validate against nothing). The password section now shows an informational message instead of a form for those accounts. Setting an initial password for a Google-only account isn't built — flagged as a natural extension point, not required now.
- Added a `danger` button variant (`x-button variant="danger"`) for the delete-account action — reuses the `destructive` design token that was already ported in Phase 0 but never used until now.
- Tests: 49 passing (9 new) — eligibility boundary (119/120/121 days, null-donation, exact-boundary), `next_eligible_date` math, donor profile update via the profile page, the unchecked-availability regression, profile page reachable even with no donor profile yet (onboarding isn't required to view/edit account settings).
- Manually verified against a live dev server with a real logged-in user and seeded donor profile — not just feature tests.

## Phase 3 — Requests core ✅ (2026-08-20)

- `blood_requests` migration matching the brief's schema exactly, plus indexes on `(status, urgency)` and `blood_group` since those are the feed's actual query/sort/filter columns.
- Routes match the brief's Section 6 literally, including the `{request}` parameter name (`Route::resource('requests', ...)->except(['edit', 'update', 'destroy'])` + a separate `fulfill` POST) — no edit/update/destroy on purpose, requests aren't editable once posted, only progressed through status or left to expire.
- `BloodRequestPolicy`: `viewAny`/`view`/`create` open to any authenticated user, `fulfill` restricted to the requester and only while status is `open` or `donor_found` — can't re-fulfill an already-fulfilled or expired request. Hit and fixed a real gap: the base `Controller` class Laravel 12 scaffolds is empty, no `AuthorizesRequests` trait, so `$this->authorize()` doesn't exist until you add it — every policy-based check in this phase was silently 500ing until that one-line fix.
- `DashboardController` (single-action, matching the brief) is the live triage view: stat cards (active count, critical count, fulfilled-today, registered-donor count — all real queries, not placeholder numbers like the landing page's intentionally-static preview), blood-group + hall filter chips (plain query-string links, no client-side framework needed), urgency-then-recency sorted feed of open requests only.
- `BloodRequestController@index` (`/requests`) is a separate, simpler paginated archive of every request regardless of status — the brief lists both a dashboard route and a full resource controller; splitting "urgent live view" from "browse everything" gives each one a real, distinct purpose instead of building the same screen twice.
- Fulfill is a simple one-step-at-a-time status advance (open → donor_found → fulfilled) for now — picking a *specific* confirmed donor needs `request_responses`, which doesn't exist until Phase 4. Flagged, not faked.
- Request detail page has a real status-tracker stepper (not from the reference — no screen for this exists there, designed consistent with the established token/component system) and a responder list is deliberately not shown yet, same Phase 4 dependency.
- `requests:expire` command + hourly scheduler entry in `routes/console.php`, and a `* * * * * php artisan schedule:run` cron entry added directly on the `skoder` account for `blood.deshlet.com` (appended alongside the existing `tali.deshlet.com` entry, didn't touch it) — confirmed live via `php artisan schedule:list` on production.
- Tests: 63 passing (14 new) — feed shows open-only, urgency sorted ahead of recency, blood-group filter, hall filter (joins through the requester), create + validation, status advance both steps, non-requester forbidden, already-fulfilled requests reject a second fulfill, expire command (stale expires / not-yet-stale untouched / already-fulfilled untouched).
- Manually walked the entire lifecycle against a live dev server with real HTTP requests: post a request through the actual form → see it on the dashboard and in the stats → advance it through both fulfill steps → watch it drop off the open-only feed → confirm the blood-group filter chip actually narrows results.

## Phase 4 — Matching & response ✅ (2026-08-20)

- `request_responses` table (unique on `[request_id, donor_id]` — a donor can respond to a given request exactly once, enforced at the DB level, not just the policy) and the `RequestResponse` model.
- Real ABO/Rh compatibility matrix (`BloodRequest::DONOR_COMPATIBILITY`), not just exact-blood-group matching — O- is the universal donor, AB+ the universal recipient, etc. Hardcoded as a const array rather than computed, because the mapping is small, fixed by medical fact (won't change), and a lookup table is far easier to verify by inspection (and to unit-test exhaustively) than blood-type arithmetic.
- `DonorProfile::scopeMatchingRequest()`: eligible + compatible donors for a request, ranked exact-blood-group-first, then same-hall-or-department-first, then available-first. Excludes the requester themselves even if they happen to be a compatible donor.
- Two `database`-channel notifications: `RequestResponded` (to the requester, sent synchronously on response — it's a single targeted notification, no reason to queue it) and `NewMatchingRequest` (to every eligible compatible *available* donor when a request is created — this one fans out to potentially dozens of donors, so it's dispatched via a queued job instead, `NotifyMatchingDonors`, fired from a `BloodRequestObserver::created` hook rather than inline in the controller).
- Brought the `notifications` table forward from its nominal Phase 7 slot, same reasoning as Phase 1 pulling `donor_profiles` forward — the feature needs it now, no reason to fake it and redo the migration later.
- Queueing decision: `QUEUE_CONNECTION=database`, but the `skoder` shared-hosting account has no supervisor/persistent-process access, so there's no long-running `queue:work` daemon. Instead `queue:work --stop-when-empty --max-time=50` is added to `routes/console.php`'s scheduler, running `everyMinute()` alongside `requests:expire`, riding the same cron that already drives `schedule:run`. Not as low-latency as a real worker, but correct and free on this hosting tier — flagged here in case this ever moves to infrastructure where a real daemon is possible.
- `RequestResponseController`: `store` (donor responds — policy-gated: not the requester, request still open/donor_found, donor eligible and compatible, hasn't already responded) and `confirm` (requester picks a specific responder — policy-gated: only the requester, only while the response is still `responded` not already `confirmed`).
- `DonorSearchController` (`/donors`) — browsable, filterable (blood group, hall) donor directory, eligible donors only. Had to be written directly rather than via `make:controller --invokable`, because `artisan` couldn't boot to run the generator once `routes/web.php` already referenced the not-yet-existing class — a one-off tooling quirk, not a design decision.
- Request detail page: "I can donate" button (donor-eligible-only, via `@can`), responder list with per-response "Confirm" action visible only to the requester, confirmed responders shown with a badge to everyone else.
- Tests: 84 passing (21 new) — compatibility matrix (universal donor/recipient, partial compatibility), ranking (exact-group-first, same-hall-first, excludes ineligible, excludes the requester), the full respond/confirm authorization matrix (compatible, incompatible, ineligible, already-responded, non-requester-confirm), both notification paths (`Notification::fake()` — sent on response, sent to matching available donors, not sent to unavailable/incompatible donors), donor search listing + both filters.
- While writing these tests, found and fixed a self-inflicted bug: the `requester()` test helper originally didn't complete onboarding (no `DonorProfile`), which broke the *confirm* test once that action was correctly placed behind the same `onboarded` middleware as everything else — fixed the helper to create a profile by default, then fixed the two tests that had been manually creating a second profile for the same user (which now violated the new unique constraint on `donor_profiles.user_id` once the helper did it automatically).
- Manually walked the full flow against a live dev server with real HTTP requests and a real MySQL session (not just feature tests): registered a requester and a compatible donor via `tinker`, logged in as the requester and posted a request through the actual form, confirmed the "I can donate" button correctly does *not* show for the requester on their own request, logged in as the donor and responded, verified the queued `NotifyMatchingDonors` job landed in the `jobs` table and processed correctly under `queue:work --stop-when-empty` (mirroring exactly what the production cron does), verified the donor's `NewMatchingRequest` notification and the requester's `RequestResponded` notification both persisted, confirmed the donor as the requester, verified the response flipped to `confirmed`, and checked the `/donors` directory page rendered and listed the seeded donor. Cleaned up the smoke-test data afterward.
